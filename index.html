TEST PROCESS

Requirements, execution, and investigation

01Define the checkStart with observable behavior+

A valid demo user should see their two tasks and be able to sign out. An invalid password should show an error and leave the dashboard hidden.

Gherkin scenarios express those outcomes. Page objects own the selectors and actions; steps hold the assertions.

See the test structure ↗
02Run & preserveMake the evidence inspectable+

GitHub Actions runs the synthetic fixtures and saves JUnit, Allure, and diagnostic artifacts. Artifact upload runs even if a test fails.

The downloaded CI artifacts were checked against their hashes. The reports linked here were generated from those saved results.

Read the run record ↗
03Diagnose & verifyUse a failure to find the cause+

The first Android run caught a locator error in the automation. Logs and the saved screenshot helped separate a test problem from an app defect.

After correcting the selector strategy, a new run tested the changed commit and passed both Android scenarios.

A real automation failure

Android test failure and resolution

The first Android CI run reached the ApiDemos screen, then the text-entry scenario stopped with an invalid CSS selector. The other scenario passed.

BEFORE · CSS INTERPRETATION#io.appium.android.apis:id/username_edit
AFTER · NATIVE RESOURCE IDid=io.appium.android.apis:id/username_edit

The explicit native locator fixed the parsing error. The corrected commit passed 2 of 2 scenarios. This was a defect in the test, not a confirmed ApiDemos defect.

What the artifacts established

The screenshot established which screen the test had reached. The error identified the selector strategy. A fresh run of the changed commit established that the correction worked. The initial failed result stays separate from the passing evidence.
